## 修订记录（Codex 核对后）

Codex 核对首版后提出四点和一处账目问题。我对照源码与数据复核，全部接受：

1. **显存风险的说法过强**：超出门槛的余量是 93.8125 MiB（替换探针）和 107.8125 MiB
   （runtime）。首版说“在 L6 之前多驻留约 80–100 MiB 的改动都会失败”并不准确，应为
   “可能耗尽余量，必须重测”。首版用来说明波动的约 29 MiB 来自 L4/L5 池，不能用来估计
   六次 L6 运行触发守卫的概率。
2. **L8 拟合不能确诊这两次运行**：此前的 trace 证明过首次加载阻塞，但这一对运行没有 trace。
   L6 改变了 L8 之前的执行时序，L8 代码相同不等于 L8 的变化与改动无关。慢掉的 5.361 s 是
   完整 outer 结果的一部分，不能先认定为噪声。
3. **“隔离门有足够效力”只是工程预期**：历史极差不是未来噪声的上界，单次 ON 也不能证明
   槽位运行总稳定在约 18 s。现有信号支持继续实验；是否通过，仍由原定的中位比和三对全胜决定。
4. **显存守卫的描述不精确**：源码（`full_cuda_ci_one_call.cpp:5144`）在每个检查点都更新空闲
   显存，但池增量只在建池后和 optimizer 完成后更新。它不是连续的峰值监测；现有资格结果仍然成立。
5. **账目**：各层收益之和为 15.1535 s，outer 收益为 15.051 s，表中补列层外开销差额约 −0.1025 s。

## 1. 代码复核

- **原生层**：`mgcv_multi_penalty_gcv_l6.hpp` 和 `rebind/drain_..._l6` 与 L4/L5 版本逐项同构。
  形状严格限定为 351×55、六个 penalty、root rank 恰为 48；有 lease 时禁止重绑定，形状或
  root 容量变化时拒绝；rebind 重传 10 个几何数组，并刷新 total_root_rank、initial_log_sp 和 generation。
- **调度层**：`L6OptimizerSlotPolicy` 只接受 2/3/5-target cohort。L6 复用同一套 worker、detach、
  Stage A 重绑定和关池流程，池在 Stage B 前关闭。生命周期等式检查（建 = 销，bind = detach =
  Stage A bind）扩展到 L6。
- **显存守卫**：`observe_capacity` 对 L4 和 L6 生效。建池后、每次 Stage A bind、optimizer 完成后和
  关池时，都读取空闲显存并更新最小值。池增量只在建池后和 optimizer 完成后（`observe_capacity(true)`）
  更新。每个检查点都要求余量 ≥2 GiB、已记录的最大增量 ≤1 GiB。它不是连续的峰值监测：worker
  运行期间没有检查点。替换探针以 10 ms 采样测得的最小值（2.092 GiB）略低于 runtime 检查点
  （2.105 GiB），两者都通过门。
- **配置门与测试**：L6 要求同时启用 L4/L5 槽位和属性缓存；九个拒绝用例覆盖每个依赖开关，
  并检查资源闭合。

## 3. 显存余量

Codex 的实测：替换探针最小余量 2,245,853,184 B（超出门 93.8125 MiB），runtime 最小余量
2,260,533,248 B（超出门 107.8125 MiB），池增量 452 MiB。我此前“替换后约 2.6 GiB”的推算作废。

其他槽位时刻的逐次波动（L4 池最小余量多为 2,575 MiB，最低 2,546 MiB；L5 建池后 2,234–2,263 MiB）
发生在 L4/L5，不能用来估计 L6 守卫被触发的概率。L6 目前只有一次 runtime 和一次替换探针的余量
数据。L6 是全程最紧的位置：将来若有改动在 L6 之前增加常驻显存（例如更大的缓存或 arena），
可能耗尽这一余量，需要先在 L6 时刻重测。

### 修订记录（Codex 核对后）

Codex 复跑了同通道分析，四份 trace 的输出与保存结果一致；GO 的核对、L6 层收益 24.260 s 与 outer
26.890 s 分开记账、L3 捕获原型优先，他都同意。另提出四点和一处账目问题。我对照数据复核，全部接受：

1. **同通道串行是直接观测，因果机制未经证明。** 首版写“与缓存无关”过强。补充核对发现，CUPTI 通道
   按 launch 分配：四份 trace 中相同的 stream id（L6 窗口 1 为 6556–6619，L7 为 6801–6844）每次落在
   不同通道上；一个 stream 一生会用多个通道（L4 槽位 stream 用 7–22 个）。通道分配受时序影响，而缓存
   改变主线程时序（关闭时 L6 的 245 次属性查询都在 prepared 创建中），可能间接改变分配。首版“32 个槽位
   stream 正好占 32 个不同通道”只看了每个 stream 的第一个 kernel，作废；改为下文“槽位模式的观察”。这是
   已有运行的观察，不是保证；L7/L3 原型必须用 trace 验证串行链确实消失。
2. **混合历史均值不能估计当前中位数的偏差。** 58 份记录混有不同 native、配置、trace 和诊断运行，只能
   说明现象反复出现。撤回“ON 中位约偏有利 2 s”，也撤回由混合均值推出的 L8 期望收益 3.8 s。当前可见的

3. **L8 的验收含义。** “L8 定向门 + outer 不退化”只能支持机制或局部优化资格；不退化的容许幅度必须预先

### 解读

1. **L6 槽位本身约省 24.3 s。** 三对的 L6 层收益为 25.628/24.260/23.417 s（中位 24.260 s）。outer 中位
   收益 26.890 s 正好来自第二对（OFF2、ON2 都是中位），其中含 L7 的 +2.873 s。26.890 s 是协议规定的
   正式数字；累计账目里 L6 槽位按约 24.3 s 计更准确，L7/L8 的差额另列。
2. **L8 的抽签不能用历史均值换算。** 本 campaign ON 的 L8 optimizer 为 16.590–16.697 s，OFF 为
   16.564/20.247/24.850 s，共享主机 ON 为 22.054 s。L8 存在抽签，但混合历史记录不能估计当前中位数是否
   偏有利。后续比较必须用同一 native 的 OFF，不能拿 368.851 s 去比其他 campaign 的单次结果（与 Codex 的
   表述一致）。
3. **Stage B 的 ON 偏慢不是 L6 造成的。** Stage B 中位 ON 多 0.605 s（三对 +1.295/+0.298/+0.318 s）。按层
   拆开，差额都在 L2–L5（L2 三对 +0.858/+0.367/+0.273 s）。这些层先于 L6 运行，两种模式执行相同代码。
   L6 层的 Stage B，ON 反而快 0.008–0.021 s。
4. **时钟与显存。** 用 nvidia-smi 200 ms 采样按层对齐（以最后一个 util>0 样本作为方法结束），六次运行
   L3–L8 的 SM 时钟中位数都是 2760 MHz，L6–L8 的最小值也是 2760 MHz，包括 L7 慢的 ON1、OFF2，
   所以 L7/L8 的波动与降频无关。整程采样峰值：OFF 为 22,373 MiB，出现在 L6（窗口模式）；ON 为
   22,077 MiB，与 L7 的采样峰值相同。L6 槽位让整程采样峰值下降 296 MiB；守卫检查点的余量
   （107.8125 MiB）是另一口径，不受影响。

### L7 波动：同通道串行（trace 观测）

Codex 指出 L7 只有一个窗口，不会继承 L6 跨窗口补位的收益。这一点正确：L7 有 44 个 setup，关键 setup
是一个约 9.36 s 的持久 kernel；按请求顺序的 32 槽补位模型为 9.52–9.54 s，槽位不能降低这个下限。
L7 的波动另有来源。

- **分布**（`history-l7-l8.json`，按 receipt 去重的 58 次）：L7 optimizer 有 21 次处于下限（超出 <0.1 s，
  其中 7 次略低于 9.372 s），1 次超出 0.1–1.0 s，26 次 1.0–1.8 s，5 次 1.8–2.5 s，5 次 >2.5 s（最大
  +9.25 s）。当前 native 的 8 次（含共享主机 2 次）中 7 次超出 1 s 以上。这些记录混有不同 native、配置
  和 trace 运行，只说明波动反复出现，不能用来估计收益。
- **trace 直接观测**：四份 trace（我的 `ktrace-run`、`ktrace-run-cache-on`，以及 Codex 用同一 ktrace
  采集的 `trace-off`、`trace-on`）共有 20 个 L6/L7 窗口。每个窗口的跨度，都等于某个硬件通道上一串
  持久 kernel 依次执行完毕的时刻：链首在 launch 后 0.010–0.022 s 内启动，相邻两个 kernel 之间隔
  0–13 ms（只有一处 66.9 ms），链未覆盖的时间每份 trace 合计只有 0.03–0.10 s。7 个窗口的链只有一个
  kernel，跨度就是关键 kernel。其余 13 个窗口中，12 个的链包含关键 kernel，超出部分等于链上其他 kernel
  的时长之和；另 1 个（`trace-on` L6 窗口 4）由一条不含关键 kernel 的链决定（3.184 + 3.472 + 0.894 s）。L7 的例子是
  `trace-off`：关键 kernel 9.363 s 在通道 4，同通道另一个 1.590 s 的持久 kernel 等它结束后才开始，
  跨度 10.953 s = 9.363 + 1.590。其余三份 trace 中关键 kernel 独占通道，L7 处于下限。
- **未 trace 的慢值也吻合**：ON1 的 17.016 s ≈ 9.372 + 7.656 s（第二长的 setup）；三次 14.18–14.28 s
  ≈ 9.372 + 4.912 s（第三长）。这只是算术吻合。
- **通道分配随运行和时间变化**：四份 trace 中，相同的 stream id 每次落在不同通道上；一个 stream 一生会
  用多个通道（L4 槽位 stream 7–22 个，L5 1–13 个），所以 CUPTI 通道是按 launch 分配的。窗口模式下，同一
  通道上的持久 kernel 有时并发、有时依次运行：L3 13–18%、L6 15–22%、L7 2–18% 的持久 kernel 在另一个
  stream 的持久 kernel 仍在同一通道运行时启动。
- **机制（假说）**：观测与 FIFO false dependency 相符：L7 的 44 个 stream、L6 每窗口的 53–64 个 stream
  共用 30–32 个通道（`CUDA_DEVICE_MAX_CONNECTIONS=32`），某个 stream 中依赖其持久 kernel 的尾部命令排到
  队首时，同通道后面的命令都要等它。但这只是时间上的吻合，没有证明（`same_channel.py` 的说明也这样
  写）。L8 的 9 个 stream 用 9 个不同通道，没有观察到这种串行；L8 的波动是已证实的首次加载排空，预加载
  的 `trace-on` 中 L8 没有晚启动。
- **缓存复核中“机制未知”的 L6 超出时间**：`ktrace-run` 的 9.21 s 来自两条同通道链（3.580 + 8.712 s；
  6.825 + 0.894 + 4.705 s），`ktrace-run-cache-on` 的 4.34 s 来自三条较短的链。直接差别在于哪些 kernel
  与关键 kernel 落在同一通道。通道分配受时序影响，缓存又改变了主线程时序，所以缓存是否间接影响这一
  差别，从这两份 trace 无法判断。
- **槽位模式的观察**：四份 trace 的 L4/L5 槽位模式（每份 2,154 + 955 个持久 kernel）中，没有一个持久
  kernel 在另一个 stream 的持久 kernel 运行于同一通道时启动，也没有晚启动的 kernel 恰在另一个槽位的
  同通道 kernel 结束时启动。同时运行的槽位 stream 不超过 32 个。L6 槽位（没有 trace）实测 18.04 s 与只用
  busy 时间的补位模型（18.34–18.39 s）相符，与此一致。这些是已有运行的观察，不保证以后的分配。

结论：L7 改用 32 槽可能消除这项抽签，但不能降低 9.36 s 的下限。收益要由原型实测：用 trace 确认串行链
消失，并测完整生命周期耗时，不能由历史均值推算。

**L3 不同**：L3 也有同通道串行。每份 trace 约 1,800 个晚启动的持久 kernel 中，53–54% 恰在同通道前一个
kernel 结束时启动；把时间平移后，偶然命中率只有 0.2–0.3%。但链只能解释部分跨度，未覆盖时间合计
11.0–16.5 s。另有 39–42% 只在其他通道的 kernel 结束时启动，偶然命中率为 11.5–14.3%，约为它的三分之一，
说明还有一种跨通道的等待，机制未查明。L3 定义跨度的 kernel 在 launch 后的 GPU 等待合计 26.6–27.7 s，
主机侧 launch 延迟只有 0.05–0.06 s。L3 的持久 kernel 为 255 寄存器 × 64 线程，按寄存器计每个 SM 最多驻留
4 个 block，4090 共 512 个；L3 grid 为 2–33 个 block（均值 13.5，等于 cohort 的 target 数）。窗口模式下，
正在运行的持久 kernel 合计 ≥480 个 block 的时间只有 2.4 s（`ktrace-run-cache-on`，共 48.7 s），所以不能
说 L3 受驻留上限约束。

### 建议

1. **下一项只做 L3 captured-cohort 原窗口／32 槽对照**（Codex 的建议，我同意）。L3 optimizer 现在是最大
   的一层（中位 49.8–50.2 s）；trace 的请求顺序补位模型为 14.8 s，约 35 s 是模型机会，不是预期收益。对照
   覆盖原来的 4,065 个 setup，保持 cohort 和请求顺序，输出逐位一致；测完整生命周期耗时、逐 setup 服务
   时间、首次加载等待（L3 optimizer 阶段首次使用 gemm N=2/3 变体）和显存增量，包括最大 33-target cohort
   的 workspace。服务时间是首要风险：32 槽持续负载会改变资源竞争，32 × 13.5 ≈ 432 个 block 只是平均
   工作量估算，L3 还有机制未明的跨通道等待，busy 时间模型可能偏乐观。可同时用 ktrace 和 `same_channel.py`
   检查槽位模式下是否仍有同通道共用。通过后再做生产共存探针；目前不直接集成 L3。
2. **L7、L8 暂不展开。** 以后重开 L8，应单独声明实验并保留 `STOP_L8_PRELOAD_PERFORMANCE`：L8 定向门加
   outer 不退化只支持机制或局部优化资格，不退化的容许幅度须预先固定，宣布完整方法提速须有重复的 outer
   收益；当前可见机会约 1.7 s，须同 native 实测。L7 槽位须先由原型用 trace 证实串行链消失，再评估收益。
