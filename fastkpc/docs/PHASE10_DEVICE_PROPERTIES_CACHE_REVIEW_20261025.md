## 修订记录（Codex 核对后）

Codex 核对首版后提出三点并指出一处勘误。我对照数据复核，全部接受：

1. **门的结论不能预判**：首版写“补跑第三对不会改变门的结论”。原门要求三对隔离运行全部获胜，
   且中位收益超过组内波动；目前只有两对隔离、一对共享主机。正式判断仍为 PENDING。
   现有结果支持继续保留默认关闭的原型。
2. **“统计上稳定”的推断过强**：28 对 4 的合并置换检验（单侧 p≈1.1e-4，Codex 复算一致）
   不满足可交换前提。历史 24 次来自四个 native，status-wait/L4/L5 配置各不相同；ON 一侧
   还混有 tracing 运行和共享主机运行。只用本轮同 native、同协议的六次运行，3 对 3 的
   精确单侧 p 为 1/20 = 0.05，已是 3 对 3 所能达到的最小值；只用两对隔离运行，最小 p 为 1/6。
   现在只能说晚层改善值得追踪，不能证明缓存稳定带来额外约 6 s。
3. **“超出最长 setup 的时间”不等于队头阻塞**：它还包含提交延迟、kernel 间隙和其他等待，
   32 槽也不保证能消除。三对的晚层收益来源也不同：第一对 L6 反而慢 0.238 s，
   主要是 L8 快 7.728 s；第三对主要是 L6 快 6.812 s。单次 trace 只能定位那一次运行的差异。
4. **勘误**：源码调用点是 9 处，不是 7 处。我首次 grep 漏掉了 `src/cuda/` 下的 `.cpp`，
   即 `cuda_status.cpp` 中的 2 处。

另外，L6 槽位模型的差额改用 Codex 按 cache-ON trace 自身服务时间计算的结果
（40.907 → 18.388 s，差 22.519 s，我复现一致）。首版的“约 22.6 s”混用了 cache 关闭 trace
的服务时间和 cache-ON trace 的 span。

## 结论

```text
实现        正确。单一 helper，按逻辑设备缓存；mutex 覆盖首次查询与发布；失败不缓存；
            调用方原有的 CUDA 检查与报错不变。9 处源码调用点全部改走 helper
复现        6 次运行硬门全真；每次请求 6,777 次（与我的 trace 计数相同），ON 只查询 1 次
节省量分解  每对的 outer 差 = L0–L5 之差 + L6–L8 之差（余项 ≤0.05 s）：
              17.85 = 9.07 + 8.77；15.17 = 9.32 + 5.90；15.27 = 8.34 + 6.91
L0–L5       中位差 8.74 s，两档各自极差 ≤1.13 s；主要在 L2（3.6–4.1 s）与 L3（4.0–5.4 s），
            与删除的属性查询吻合（主线程 7.94 s，外加 L2 worker 争用）
L6–L8       三对都偏向 ON（8.77/5.90/6.91 s），但来源不同：第一对主要是 L8（+7.73 s），
            第三对主要是 L6（+6.81 s）。同协议六次运行的精确单侧 p=0.05。值得追踪，
            未证明是缓存的稳定效果；L6–L8 的直接查询只有约 0.4 s，机制未知
判断        正式性能判断 PENDING；现有结果支持保留默认关闭的原型。约 8.7 s 的早层改善
            可由删除查询解释；晚层改善单独记账，不与后续槽位收益相加
```

## 1. 实现复核

| 关注点 | 结论 |
|---|---|
| 覆盖 | 9 处源码调用点：`cuda_status.cpp` 2、`mgcv_multi_penalty_gcv.cu` 4（该源编入五个 capacity TU）、`mgcv_single_penalty_gcv.cu`、`mgcv_fixed_sp_runtime.cu`、`dcov_batch_cuda.cu` 各 1。全部改走 `fastkpc_cuda_get_device_properties`；直接调用 `cudaGetDeviceProperties` 只剩 helper 本身 |
| 模式 | 函数内静态对象在首次使用时读取环境变量；空/0 关闭，1 开启，其他值抛异常；首次使用后不再改变 |
| 并发 | 命中和首次查询都在同一 mutex 下；首次查询期间其他线程等待，因此每个设备最多一次成功查询 |
| 失败 | 查询失败不缓存，返回原错误码；调用方的 `check_cuda` 与报错文本不变 |
| 静态性 | 缓存的是静态元数据；`computeMode` 等运行期可改的字段当前没有决策用途，报告已注明“不是设备健康检查” |
| 资源 | 只有一个 host map，没有 GPU 分配/stream/event/handle |

观察项：环境变量非法时，异常在首次调用时从一个返回 `cudaError_t` 的函数中抛出，而不是
返回错误码，所以仍会以失败结束，只是报错路径与其他 CUDA 错误不同。报告称已有测试覆盖，
可以接受。命中路径每次加锁，在 L2 的 18 个 worker 下也只是一次 map 查找和约 1 KB 复制，
开销可以忽略。

| OFF1 | 410.266 | 326.807 | 45.18 | 11.24 | 25.19 | 81.61 |
| ON1 | 392.416 | 317.735 | 45.42 | 9.96 | 17.47 | 72.85 |
| ON2 | 391.504 | 318.213 | 41.09 | 11.58 | 18.75 | 71.41 |
| OFF2 | 406.673 | 327.534 | 44.51 | 11.25 | 21.55 | 77.31 |

| ON3（共享主机） | 389.392 | 318.064 | 42.53 | 10.00 | 16.92 | 69.45 |

| 我的 trace，cache 开启（native 994c43d3） | 391.812 | 319.452 | 43.42 | 9.96 | 17.08 | 70.47 |

两次 trace 运行分别使用不同 native，且带 CUPTI 注入，只用于定位，不进入性能比较。

**L0–L5（可由删除查询解释）**：三对之差为 9.07/9.32/8.34 s，中位数之差 8.74 s；
OFF 与 ON 各自的极差只有 1.13/0.48 s。主要来自 L2（−3.6 至 −4.1 s，其中 `l2_prepared`
约 −2.0 s、L2 Stage A 约 −2.1 s）和 L3（−4.0 至 −5.4 s）。全程 `prepared_build`
由 9.10/9.22/9.40 s 降为 1.44/1.42/1.51 s。traced 对照中，查询从 6,777 次降为 1 次，
L0–L5 减少 9.8 s（L2 −3.6、L3 −5.9 s）。这与 trace 中被删除的主线程查询时间
（7.94 s；L3 为 5.24 s，L2 为 2.13 s）加上 L2 worker 之间的争用（p90 21 ms）吻合。

观察：三对中 L3 的 optimizer host 时间 ON 都略长（0.67–1.71 s），但 L3 层总耗时仍减少
4–5 s。对比历史运行的波动（sd 约 0.9 s），这一差异尚不足以判断。

**L6–L8**：三对都偏向 ON（8.77/5.90/6.91 s），但各对来源不同：

| 对 | L6 | L7 | L8 |
|---|---:|---:|---:|
| OFF1/ON1 | −0.238 | +1.277 | +7.728 |
| OFF2/ON2 | +3.421 | −0.329 | +2.803 |
| OFF3/ON3（共享主机） | +6.812 | +0.005 | +0.097 |

（正数表示 ON 更快。）L8 仍符合首次加载串行化模型：每次运行的 L8 都等于 14.94 s 加上
被串到前面的一或两个完整 setup，6 次残差 ≤0.016 s；OFF 的超出量为 9.88/6.23/1.70 s，
ON 为 2.16/3.45/1.62 s，第一对的差主要来自这种排序的随机结果。L6 的差主要出现在
第二、三对。

## 3. 晚层差异能说明什么

**统计**：把 28 次 cache 关闭运行与 4 次 cache 开启运行合并做置换检验，L6+L7+L8 均值差
6.38 s，单侧 p≈1.1e-4。但这些样本不可交换：历史 24 次来自四个 native，status-wait、
L4/L5 配置不同，ON 一侧还混有 tracing 和共享主机运行。只用本轮同 native、同协议的
六次运行，3 对 3 完全分开，精确单侧 p 为 1/20 = 0.05，已是这一设计能达到的最小值；
只看两对隔离运行，最小 p 为 1/6。结论：晚层改善值得继续追踪，不能证明是缓存的稳定效果。

**traced 对照**（`compare_windows.py`，请求顺序与修订版复核相同；仅这一对运行）：

| 指标 | cache 关闭 | cache 开启 |
|---|---:|---:|
| L6 窗口 span 之和 | 45.80 s | 40.91 s |
| L6 各窗口最长 busy 之和 | 36.60 s | 36.58 s |
| L6 超出最长 setup 的时间 | 9.20 s（窗口 2、4：+3.6/+5.6） | 4.33 s（窗口 1–3：+1.6/+0.9/+1.8） |
| L6 晚于 100 ms 启动的 setup | 31 | 26 |
| L3 超出最长 setup 的时间 | 10.12 s | 9.54 s |
| L7 / L8 span | 9.38 / 16.61 s | 9.37 / 16.70 s |
| L8 首个 optimizer 单独运行 | 1.686 s | 1.685 s |

在这一对中，L6 各窗口最长 busy 之和相同，差别在“超出最长 setup 的时间”。这部分包含
队头阻塞、提交延迟、kernel 间隙和其他等待，trace 无法把它们完全分开。机制也未查明：
窗口模式的 worker 路径里没有属性查询（关闭时 L6 的 245 次全在主线程的 prepared 创建中）；
两种模式的 stream→channel 映射同样呈伪随机，每窗口使用的 channel 数相近；6,814 个
stream 中只有约 2,500 个一生只用一个 channel。单次对照不能解释其他重复运行，
尤其是第一对的晚层差主要来自 L8。

## 4. 对后续工作的影响

同意 Codex 的次序：补齐第三对隔离运行 → 在 cache-ON 下做 L8 定向预加载 A/B →
做 L6 原序槽位原型。

1. **记账**：约 8.7 s 的早层改善与删除属性查询高度吻合，可按此记录；晚层改善单独记账，
   不与后续槽位收益相加，也不外推到其他改动。
2. **L6 槽位**：原型以 cache-ON 为基线，用同一口径比较。Codex 用 cache-ON trace 自身的
   服务时间重算：当前窗口 span 40.907 s，32 槽模型 18.388 s，模型差 22.519 s
   （我复现一致；随机顺序 p5/p50/p95 为 14.6/18.0/21.2 s）。原型要验证的是 32 槽能否减少
   上述等待，以及持续负载下的服务时间、容量和完整方法收益；模型数不是承诺。
3. **后续 A/B 的报告方式**：L8 预加载等改动的 A/B，建议分别报告 L0–L5 与 L6–L8。
   L6–L8 的运行间波动约 3 s，且来源随运行变化；只看 outer 容易把这里的变化记到错误原因上。

## 补记（2026-10-27，L6 超出时间的 trace 观测；同日按 Codex 核对修订）

第 3 节的 traced 对照中，L6“超出最长 setup 的时间”（9.20 s 对 4.33 s）当时机制未查明。补充分析发现：
每个窗口的跨度都等于某个硬件通道上一串持久 kernel 依次执行完毕的时刻，链未覆盖的时间每份 trace
合计只有 0.03–0.04 s。cache 关闭时是窗口 2（3.580 + 8.712 s）和窗口 4（6.825 + 0.894 + 4.705 s）两条链；
cache 开启时是窗口 1–3 三条较短的链。直接差别在于哪些 kernel 与关键 kernel 落在同一通道。这与 FIFO
false dependency 相符，但没有证明。首版补记写“与缓存无关”，过强：CUPTI 通道按 launch 分配，相同的
stream id 在不同运行中落在不同通道，而缓存改变了主线程时序（关闭时 L6 的 245 次查询在 prepared
创建中），所以缓存是否间接影响这一差别，从这两份 trace 无法判断。这仍与修订记录中“不能证明是缓存的
稳定效果”的判断一致。详见 [L6 槽位 runtime 复核](PHASE10_OPTIMIZER_L6_SLOT_RUNTIME_REVIEW_20261026.md)
的“最终核对”。
