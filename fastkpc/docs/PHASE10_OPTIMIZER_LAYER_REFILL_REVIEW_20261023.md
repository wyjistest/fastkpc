## 1. 复现

| 档 | native-call 中位数 s（范围） | 分段工作中位数 s | 计入建销 s |
|---|---:|---:|---:|
| P | 106.124（105.261–111.142） | 107.993 | 107.993 |
| A | 106.154（101.942–110.304） | 106.161 | 107.953 |
| R | 31.787（31.631–31.822） | 31.791 | 33.580 |

六轮同轮 R/A：0.301、0.304、0.288、0.310、0.297、0.298。P 与 A 几乎相同：在有窗口
屏障的形状下，native 调用时间接近。P 的建销仍约 1.84 s，计入完整生命周期后两档接近；
这说明建销不是约 74 s 调度收益的主要来源，不等于它没有成本。

整层与双窗口的差别值得注意：同一机制在 L5 双窗口上是 0.551，在整层上是 0.299。
窗口屏障每个窗口都要等最长的 setup，15 个窗口共付 15 次；连续补位只在层末付一次尾部。

## 2. R 的时间由什么决定

`tail_model.py` 读取 Codex 的 `profile-kernel-timeline.csv`。逐 setup 服务时间取
“首个 kernel 开始 → 最后 kernel 结束”。同一 setup 在 R 与 A 中的服务时间中位比为
0.9943，总服务时间 A/R 为 854.980/849.034 s，支持总体服务量接近。
不能据此说每个 setup 都不变：比值 P95 为 1.099、最大 1.311，48 个 setup 超过 1.10。
这些差异也包含运行波动，不能直接归因于 contention。

| 项 | 秒 |
|---|---:|
| R 实测 kernel 跨度（profile） | 31.554 |
| 模型：32 槽，原顺序 | 31.536 |
| 模型：A 的服务时间、32 槽、原顺序 | 31.775 |
| 模型：32 槽，最长者先发 | 26.791 |
| 下限 max(Σ/32, 最长) | 26.532 |
| Σ 服务时间 | 849.0 |
| 最长单 setup（#251，W4） | 10.481 |

在 R 中，最后一个 setup 在 25.74 s 开始。此前在途不足 32 的时间只有 0.346 s（1.3%），
包括启动阶段与补位间隙；启动 0.5 s 之后最低为 24。之后的 5.79 s 内在途持续不足 32。尾部由 #861（W14，8.12 s，23.43–31.55 s）决定；#692（W11，8.23 s）在
18.60 s 开始。最长的 #251 在 6.09 s 开始，不在尾部。

## 3. 剩余的两个杠杆

**顺序**：固定服务时间模型中，最长者先发把 L5 从 31.5 s 降到 26.8 s（−15%），接近该模型下限，尚非实测。但这需要事先
知道时长：最长的 #251 只有 4 个 target，而 955 个 setup 中 792 个有 8 个 target，
target 数不是可用的预测量。维持“最后再评估”。

**并发超过 32**：在服务时间不变的假设下，模型给出：

| 并发 | 原顺序 s | 最长者先发 s |
|---:|---:|---:|
| 24 | 39.713 | 35.599 |
| 32 | 31.536 | 26.791 |
| 40 | 26.494 | 21.409 |
| 48 | 23.341 | 17.837 |
| 64 | 19.365 | 13.354 |

两个前提都未验证：

- **队列**：在当前 32-connections 配置下增加在途 stream 有队列共享和阻塞风险；
  具体映射不是公开的一对一合同。此前探针中观察到长 kernel 后续的依赖命令
  （同 stream 的后续 kernel、blocking-sync event record）影响共享队列。
  延后后续命令等办法只是后续待测假设，不能据此保证超过 32 后可消除阻塞。
- **SM 容量**（`kernel_resources.py`）：optimizer kernel 每个 target 一个 64 线程 block，
  每线程 255 个寄存器，无 shared/local memory。按寄存器，每个 SM 最多驻留 4 个 block，
  128 个 SM 共 512 个。L5 平均每个 setup 7.14 个 block：32 个 setup 约 228 个（45%），
  64 个约 457 个（89%）。每 SM 从约 2 个 block 增加到约 4 个时，FP64 单元共享是否拖慢
  单个 block，没有数据。
  512 是理论驻留 block 上限，228/512 不是实测 GPU 利用率，不能作为并发收益承诺。

这是一项独立的后续诊断，不应并入槽位池原型。

## 4. 槽位池的显存口径

`prepared_memory.py` 按 Codex 容量检查的逐对象 free-memory 变化统计：

| target 容量 | application buffer | 实占 | setup 数 |
|---:|---:|---:|---:|
| 8 | 6.68 MiB | 16 MiB（偶见 18/20 MiB） | 693（+86/13） |
| 2 | 1.94 MiB | 10/12/14 MiB | 57/6/2，共 65 |
| 4 | 3.52 MiB | 12/14/16 MiB | 48/7/1，共 56 |
| 3 | 2.73 MiB | 12/14 MiB | 37/5，共 42 |

典型增量近似 buffer 按 2 MiB 取整，再加约 8 MiB，另有 2–4 MiB 增量。来源未确定（可能是每个对象的
cuBLAS handle 或 stream 资源）。槽位按该层最大容量分配时约 16 MiB，32 个槽约 0.5 GiB，
只是该 L5 形状的初步预算。输出保存区、arena、库缓存和其他存活资源必须计入；
与 11 GiB component cache 共存须单独做 runtime 联合容量资格。

## 5. 其他层：先估值，再集成

四次 status-wait 运行的逐层中位数（`level_stages.py`，单位秒）：

| 层 | optimizer | stage A | stage B | 层总耗时 |
|---|---:|---:|---:|---:|
| L2 | 6.906 | 15.351 | 54.767 | 94.778 |
| L3 | 49.302 | 0.616 | 60.235 | 127.296 |
| L4 | 87.424 | 0.247 | 19.747 | 117.403 |
| L5 | 104.148 | 0.102 | 7.700 | 117.172 |
| L6 | 45.535 | 0.022 | 1.264 | 48.407 |
| L7 | 10.595 | 0.004 | 0.285 | 11.244 |
| L8 | 19.252 | 0.001 | 0.266 | 19.629 |

- L4 的 optimizer（87.4 s、2,154 setup、34 个窗口）是下一个最大的对象。
- L3 的 stage B（60.2 s）大于其 optimizer（49.3 s）；补位只作用于 L3 的较小部分。
- L6 只有 245 个 setup、4 个窗口，可能受单个长 setup 限制，收益要看其时长分布。
- L5 的尾部（约 5.8 s）与其 stage B（7.7 s）同量级；补位落地后，可以考虑让 stage B
  利用尾部。这是更后面的事。

R 自身服务时间重建 R 的 0.06% 偏差是同次 trace 的拟合；用 A 的服务时间预测 R 为
31.775 s，与 R kernel 跨度 31.554 s 相差约 0.7%，提供了 L5 的跨配置支持，仍非跨层验证。
后续逐层 profile 应固定 status-wait=1、CUDA connections=32 及 native，并记录 host/API
间隙和完整 pipeline。模型仅筛选 L3/L4/L6 的机会，不替代槽位上传/输出保存成本或实际重放。

## 6. 建议

1. 同意 Codex 的范围：在隔离原型中验证槽位重绑定、原 target cohort 与顺序、完整
   输出位值、结果保存与 token/event 生命周期、补位期间无资源建销，以及几何上传与输出
   转移的净成本和显存峰值。槽位数可先取 worker 数（32），需要预取时再加少量。
   必须先完成输出保存再解除 lease，旧 token 不得访问后续 generation；
   维持实际 target_count，不按最大容量补齐数值 cohort，并验证失败清理。
2. 并行或紧随其后做第 5 节的逐层估值。
3. 顺序优化与超过 32 的并发都放在槽位池和 runtime 集成之后；后者需要第 3 节两项
   前提的独立诊断。
